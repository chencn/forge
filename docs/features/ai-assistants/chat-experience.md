# AI 助手：聊天细节与当前项目原生历史

本轮接通原生历史、模型参数、用量和聊天时间线。协议以官方定义为准；模型管理同时参考本地 `desktop-cc-gui-main` 的 `CliEngineSettingsCard.tsx`（增删、按引擎保存）与 `engine/models/claude.rs`（保留别名 ID、显示配置目标）。

## 已实现流程

### 1. 当前项目历史

1. 总开关开启、项目打开后，侧栏查询 Forge 会话，并发现当前项目的原生会话。切换项目后只展示新项目；迟到的旧查询不更新新项目。
2. Claude 从 `CLAUDE_CONFIG_DIR/projects`（默认 `~/.claude/projects`）发现；Codex 从 `CODEX_HOME/sessions`、`archived_sessions`（默认 `~/.codex`）发现。
3. 校验记录内的 cwd 和原生 ID，不根据目录名称猜归属。兼容 Windows 大小写、斜杠和 extended-path 前缀；不跟随历史目录中的符号链接，不导入子代理会话。
4. 以 provider + native ID 与已有 Forge 记录去重。列表发现只读取有界头部，打开时才导入正文。
5. 原生文件始终只读，唯一的例外是用户对某一条会话明确勾选「同时删除 CLI 原生记录」（见第 8 条）；Forge 在自己的存储中保存镜像和追加游标。一次同步最多约 500 个投影事件或 4 MiB 原始记录（单行边界允许略超），前端沿用有界分页。JSONL 半行留待下次刷新，不修复、不截断原生文件。`role=user` 不等于真人打的字：Codex 把 `# AGENTS.md instructions` + `<INSTRUCTIONS>`、`<environment_context>`、`<subagent_notification>`、`<codex_internal_context>`、`<turn_aborted>` 都写成 user 记录（本机 187 条里 51 条是这种注入），Claude 则有 `<task-notification>`、`<system-reminder>`、`<local-command-stdout>`、`<command-name>`/`<command-message>`/`<command-args>`、`<user-prompt-submit-hook>`。投影按成对标签整块剥掉这些注入，剥完不剩人话就不产生用户气泡，也不拿它当标题素材（会话列表里真出现过一条标题就是「# AGENTS.md instructions」）；剥完还剩人话就只留人话，助手引用同样标签时一个字不动。旧日志里已经写进去的那几条改不了——日志只追加、序号不能断——所以分页、轮次索引和正文搜索读出来时按同一份判定再挡一次。
6. 侧栏刷新、窗口重新聚焦会重新发现会话；已打开会话在聚焦、重新打开及运行状态变化时加载新增记录。首屏取的是**最新**一页（后端 `Window::Before(u64::MAX)`），往上翻才逐页取更早的记录——几百轮的老会话打开即停在当前对话，不用从第一行滑到最后。翻页不拦发送：发送走同会话 FIFO，忙时排队（每会话 32 条、全局 256 条，超限如实报队列已满）。
7. 继续聊天使用原 native ID，经现有 `thread/resume` / `--resume` 恢复，不把旧对话重新作为 prompt 发送，也不重放旧审批。Forge 本轮结束后推进原生镜像游标，避免再次导入同一轮输出。
8. 删除默认只删 Forge 镜像，并记录隐藏标记，后续发现不会把它重新加回来。确认框里勾了「同时删除 CLI 原生记录」才动 CLI 那一份，且不可恢复：Codex 发 app-server 的 `thread/delete`（本机 0.164.0 隔离验证：`sessions/` 与 `archived_sessions/` 里的 rollout 都会真删；磁盘上没有该线程时回 `-32600 no rollout found for thread id …`——从没发过消息的空线程根本不落盘，这跟删除成功等价，按已删处理），Claude 没有逐会话删除入口，按 CLI 自己 `claude purge --dry-run` 列出的会话级清单逐项删：discover 登记过的那条 `projects/<项目>/<原生 ID>.jsonl` 和它的同名附属目录（tool-results、subagents 都在里面），外加按会话 ID 存的 `tasks/<ID>`（task 清单）、`file-history/<ID>`（文件编辑历史）、`session-env/<ID>`（会话环境）。路径校验自己把住：transcript 必须仍是 `projects` 锚点下的普通文件且文件名就是那个原生 ID，后三项的锚点必须是配置目录下的真目录，任何一条不满足就拒绝删除并如实报错，宁可留孤儿文件也不能拿别人的日志去赌一次拼路径。删除按「会话组」逐个原生 ID 走（父会话加它各级子代理——Codex 的 delegate 能让子代理再开子代理，所以按 `parentSessionId` 滚到不动点，只收一层会把孙代理留成侧栏进不去的死记录），Codex 端因此会对子线程各发一次 `thread/delete`，Claude 端子代理的 transcript 本来就在父会话的 `<ID>/subagents/` 里随父一起走；Codex 的 `thread/delete` 之后还会顺手收掉它按线程 ID 留下的 `thread-writer-locks/<ID>.lock` 与 `tui-thread-reference-capabilities/<ID>`（实测 CLI 自己不动这两个，本机 10 条能力标记里就躺着一条孤儿；被活进程占着删不掉就留着，两个都是可重建的空文件）。顺序钉死为先原生后镜像：原生任一条失败就整笔中止，绝不留下「镜像没了、原生还在却被永久屏蔽」那种既没删到又再也导不回来的中间态；原生真删成功后隐藏标记反而要撤掉——它没有过期机制，留着就是只增不减。重命名以 Forge 的标题为准并加锁（Codex 同时写回原生线程名；Claude 没有写入口，只落 Forge 侧）。
9. 正文搜索直接扫 Forge 的 JSONL 原文，不建倒排索引：事件日志是唯一真相，索引一旦落后就会搜出一句没人说过的话。扫之前先合并流式分段，规则与前端渲染一致，所以连起来说的一句话能整句命中。上限钉死为 2000 个会话、单会话 32 MiB、单次总量 128 MiB、合并文本单会话 16 MiB、单会话最多 5 条命中、一次最多 200 条；跨到上限返回 `truncated`，界面必须显示「没扫完」，`skipped` 另计读不出元数据的会话，`scanned` 只数真正打开过的会话。匹配只对 ASCII 大小写不敏感——折叠后字节仍对齐，偏移才敢拿去给前端 `slice`；中文按原样比较，宁可漏一条也不把片段切错位置假装匹配过。命中偏移按 UTF-16 码元报数，emoji 在 JS 里占两格，按 Rust 的 `chars()` 报会切歪半格。
10. 搜索不持 `IO_LOCK`：一次扫描最多读上百 MiB，握着锁会把正在运行的会话的事件写入一起卡住。代价是可能读到作者正在追加的尾部，所以逐行解析、半行直接丢弃——搜索只读原文，不修复、不截断，也不要求会话空闲。命中不承诺是全部，只承诺报出的每条确实在日志里，并按回合时间从新到旧排。
11. 归档只是 `meta.json` 上的一个布尔位，事件日志、原生会话绑定、CLI 侧记录都不动：不删记录、不停运行中的任务，随时可取消。列表仍由后端 `ai_runtime_list` 带 `archived` 标记一次返回，前端只在选择性持久化时写 `archived: true`，未归档保持无字段，让新旧缓存在字符串上等价。搜索范围（含不含已归档）和查询词共同决定结果能否显示，界面只认最新一次请求的令牌，迟到的旧答案一律丢弃；空查询不落磁盘。设置页的「归档会话」页签（同样只在 AI 总开关开启时出现）是这批收起会话的收尾入口：只列已归档的顶层会话（子代理跟着父一起走），逐条复用单条删除的完整序列而不另写快路径；按 CLI 分「全部 / Claude Code / Codex」三个页签，页签上带各自的条数，而「删除全部」只删当前页签看得见的那些——`ai_runtime_delete_archived` 因此收一个 `provider` 参数由后端按同一条件扫归档清单，界面筛的是 Codex 却把 Claude 的归档一起清掉是不可接受的。这一页没有可编辑的详情，所以走单列铺满而不套左右两栏的管理页骨架：右边那一栏本来只会放一句说明，白占一半宽度。整批的原生删除合并成一次 app-server 连接，删不掉的按会话指名报出原因并留在列表里，不把整批的成功与失败混成一锅。

### 2. 模型和思考强度

- 紧凑工具栏提供默认/沿用会话、模型选择与思考强度；自定义模型 ID 只在设置页的「自定义模型」区增删，会话的模型列表只负责选择与刷新。
- Codex 设置页控件通过官方 `config/read` 读取当前项目的有效模型、强度、权限和服务等级，并直接选中真实值，不提供伪造的“沿用配置”选项。切换控件使用 `config/batchWrite` 修改项目层并回读；任务入队时再次读取并冻结模型、强度与服务等级，后续切换只影响新任务；输入区本轮选择的权限不在这里冻结。项目信任是独立的启动确认。
- 模型调用 ID、显示名、目录项 ID 分开保存。已知的显示名和大小写变体解析到唯一调用 ID，例如 `GPT-6-Astra` 不会另建为 `gpt-6-astra` 之外的模型；未知 ID 保留原样。
- 模型目录首先读取应用配置目录的 `ai-models.json`（Windows 默认 `%APPDATA%/app.forge.desktop/ai-models.json`）。`catalogs` 保存探测目录，`customModels` 按 `claude` / `codex` 保存自定义 ID 数组；两者原子合并写入，后台刷新不会覆盖自定义项。缓存不存在或损坏时使用内置默认/别名，仍可选择 CLI 默认模型；自定义 ID 只能先在设置页添加。
- Codex：每次应用启动自动在后台尝试一次 `initialize` / `model/list`，成功写回 JSON，失败保留原目录，可手动重试。不创建 thread 或发送 turn，不占用会话生命周期锁，也不禁用模型选择或发送。Fast 发送读取缓存，不再临时启动模型探测。模型和档位来自 CLI 返回的 `supportedReasoningEfforts`。实际请求把 `model` 写入 thread 参数，并把 `model` / `effort` 写入 `turn/start` 顶层。
- Claude：提供 `sonnet` / `opus` / `haiku` 别名，读取环境、用户和工作区 settings 的 `ANTHROPIC_DEFAULT_*_MODEL`；槽位配置后列表直接显示目标模型 ID，并标注“自定义 sonnet 模型”，调用仍使用别名。自定义 ID 在设置页明确添加、删除并保存 JSON。为避免初始化 hooks，不另起 Claude 会话发现模型；这些不是已验证的账号可用目录。
- Claude 实际启动追加独立参数 `--model` / `--effort`，不经过 shell 拼接。管理员限制、供应商可用性和模型替换仍由官方 CLI 执行。
- 请求模型与实际模型分开：实际模型优先来自 Claude assistant/modelUsage、Codex thread 响应及 model/rerouted 通知；未报告的实际思考强度显示未知，不把请求值冒充确认值。
- 模型供应商是「端点 + 密钥 + 模型」的预设，不是模型目录：保存时不联网、不改任何 CLI 文件；写进 CLI 真正的配置是另一件事，在「AI 编程助手」里绑定供应商后点「应用」才发生（Claude 的 settings.json env，Codex 的 env 与 config.toml / auth.json）。页面沿用设置页的左右两栏：左边一列供应商（名称、地址、类型徽标、「添加供应商」），右边是选中供应商的表单。字段按 codeg `ModelProviderSettings` 的对话框逐项对齐：名称（例如 OpenAI、Anthropic）、API 地址（https://api.openai.com/v1）、API 密钥（sk-...，编辑时「留空则保持不变」）、智能体类型，再按类型给模型——Claude 六个槽位（主模型 / 推理模型（思考）/ 默认 Haiku / 默认 Sonnet / 默认 Opus / 默认 Fable）+「自定义模型 ID / 名称 / 描述」，Codex 一个模型（候选来自 CLI 自己的模型清单，读不到就退回手填并说明原因）。**编辑时密钥不显示，留空表示沿用原值**，**类型创建后只读**（选择器禁用并写明不可修改，后端也拒），这两条与 codeg 一致；名称、地址、新建时的密钥必填。仍被某个 CLI 绑定着的供应商不能删，「绑定模型供应商」那一栏不该被删成一个「绑定的供应商已不存在」。Claude 的自定义模型选项三项对应 `ANTHROPIC_CUSTOM_MODEL_OPTION*`（本机 settings.json 里就在用这三项），在 CLI 的 /model 选择器里多出一项。Codex 侧 codeg 用的是整份模型清单编辑器（官方条目 + 自定义克隆），Forge 目前仍是单个模型 ID 加候选清单，这是尚未对齐的一处；清单之外的裸 ID 没有可核实的参数，Codex 会按默认参数处理，未必可用。

- 权限在输入区常驻：Codex 可选只读 / 按需审批 / 项目内自动允许 / 完全访问，未选择时沿用项目原生配置（`inherit`）；本轮选择原样随请求发送，入队只冻结模型、强度与服务等级，不会再被压回 `inherit`。Claude 默认按需审批。完全访问每次选择都需独立确认。项目信任与权限模式是两回事。Forge 会记住上次的权限模式（只读 / 按需审批 / 自动允许编辑 / 完全访问），同一会话、新会话与重启后都沿用，直到改回其他模式。
- Codex Fast 在输入区常驻；只有模型目录明确提供 Fast 等级时才能开启，未提供时说明原因。后端按目录的真实 ID 发送，关闭显式恢复 `default`。不调用模型来探测账号资格，也不把选中状态声称为服务器确认。

### 3. 上下文组成与时间线

- 上下文概览常驻显示已用 / 窗口 / 比例，窄栏保留文字；K 是十进制千 token，不是 KB。详情点击浮出，不撑高输入区。
- Claude 成功回合结束后查询 `get_context_usage(detail: summary)`，获取系统提示词、MCP、会话消息等分类；显示 token 数与窗口占比，并展开实际返回的系统提示分段、工具、记忆文件、消息组成等。标注 CLI 本地估算和采集时间，不调用逐分类 token-count API。
- `kind` 区分已用、剩余、压缩预留与窗口外延迟加载项；明细不重复相加。分母保守标注为压缩窗口，不能承诺等于模型硬上限。
- 新回合、压缩、模型变化使旧快照过期；过期比例不用于常驻概览，浮层保留旧快照并明确标记。未报告显示未知，而不是零。
- Codex 0.163.0 稳定 app-server 仅提供总量：概览使用 `tokenUsage.last` 与 `modelContextWindow`，不把累计 `total` 当上下文。芯片两家都能点开——点开的是压缩那一层（压缩对 Codex 同样是主动操作），分类明细才只给 Claude，Codex 那一层直说没有明细；`/context` 命令本身仍仅适用于 Claude。
- 上下文浮层已移除输入、输出、缓存、推理用量和费用；这些消费统计不是用户要求的上下文组成。协议证据、采集降级与验证边界见 [上下文组成](context-composition.md)。
- 按顺序展示正文、公开思考/推理摘要、工具、审批、提问、计划、重试、压缩和文件变更。活动审批即使在较早记录中仍可见。
- 工具摘要区分脚本/命令、读取、搜索、增删改和移动，直接显示目标文件及已报告的行号。详情保留 Claude 结构化结果和 Codex fileChange，展示真实 diff 旧/新行号、读取内容、工作目录、输出、退出码与耗时；缺失行号不猜测，staged 不冒充已写入。明细与原始 JSON 展开后才构造，避免折叠的大文件拖慢流式输出。
- 会话侧栏、打开标签与项目菜单共享任务状态。已访问工程后台继续轮询，Forge 事件即时更新。Claude 有效 PID 登记的 busy/waiting 才算外部任务，idle 不算；Codex 写锁加真实任务起终边界共同判断，持锁不等于执行——但「持锁不挡徽标」不等于「持锁能发送」：`thread/resume` 只要写锁有人握着就拒，所以发送和队列调度过的是 `externally_blocked`（徽标状态 **或** 原生写锁在握），不是徽标那一个判定。unknown 不阻止发送；写锁探测读不到也不阻止，宁可让 CLI 报错也不把发送堵死。
- 正文支持安全 Markdown 与高亮，复制按代码块给；不自动加载外部媒体。不解析 redacted/encrypted thinking，不声称展示供应商隐藏推理。

### 4. 停止、排队顺序与状态词表

1. 两把锁各管各的：`registry::LIFECYCLE` 串行化跨会话的「发送、排队、停止」决策，`store::IO_LOCK` 只管事件日志写入。唯一的嵌套方向是前者套后者，worker 的批量 flush 只拿 `IO_LOCK`，所以不存在反向等待。
2. 停止拆成「置位」和「等待清理」两步：锁内只做「查到哪一个、决定停它」（`request_stop` / `flag_stop`），等 worker 真正退出（`wait_until_stopped` / `wait_stopped`）一律放到锁外。等待有自己的 15 秒兜底上限，超时就报「任务仍在清理，尚未关闭；请稍后重试」，不假装已经停下。回合自己那边在 interrupt 之后最多再让 3 秒就返回 `cancelled`，随后 `Process` 析构关闭写入端并按进程树清理子进程，所以正常情况远快于这个上限；上限兜住的是 worker 卡在管道写入或磁盘上的病态情况。
3. 唯一的例外是删除会话：它仍在锁内等到底，因为「证明回合已退出」和「抢到会话租约再删目录」必须是一步——中间放锁会让刚发起的新发送踩进正在被删除的会话。删除同样先清掉本会话的排队项，并且拒绝归属不匹配的回合。
4. 「全部停止」和「关闭项目」先清空队列，再放回合去死。worker 收尾顺序是 `worker.finish` → 释放会话租约 → `run.finish()` → `schedule_next`，最后一步会重新拿 `LIFECYCLE`；反过来做，锁一释放就可能把用户刚刚要求「全部停止」的任务又启动起来。取消排队项一律按 run id 精确命中，落成 `cancelled` 后绝不自动重放。
5. 队列顺序：`queueIndex` 只由顺序变更事件写出，并且一次写全该会话的每一项——半贴标签会让刚贴上的项排到没贴的旧项前面。没贴过的项按回合时间（seq）排在带索引的项之后，前端 `(queueIndex ?? 最大值, seq)` 与后端 `VecDeque` 顺序一致；运行中的回合不进队列视图。
6. `waitingExternal` 只属于队首：入队和顺序变更共用同一个判定（`queued_status(是否队首, 外部是否占用)`）。此前入队把每条新消息都标成等待外部，同一条队列会出现两项都「被外部进程卡住」，而排在后面的那项其实只是在排队首——真实原因只是排位靠后。队首到底算不算被外部挡住，必须在 `LIFECYCLE` 内一起判定（本会话没有 Forge 回合 + 外部占用探测同时成立），否则探测结果与真正启动之间还能插进一个回合。
7. 队首启动失败时不再往下弹队列：失败几乎都是会话级原因（会话目录、租约、进程创建），继续弹会在一次抖动里把整队最多 32 条提示全部判死。这一条如实落 `failed` 并带错误，其余排队项留给 1 秒一次的队列监控器重试管首；没有任何 CLI 启动过，所以重试不等于自动重发。
8. 状态词表两边各一份、靠字面量对齐、没有代码生成：Rust `ai_runtime/task_status.rs` 与前端 `src/lib/aiTaskStatus.ts`。`EMITTED` 与 `AI_TASK_BACKEND_STATUSES` 是同一张冻结表，两边测试都断言它等于 `queued / waitingExternal / running / completed / cancelled / failed`，任何一侧偷偷加一档就会红。「未结束」与「终态」必须互补且互斥，排队档是未结束档的子集。`submitting` 只在前端 IPC 往返期间存在，绝不落盘：发送回执的状态只有认出是后端六档里「还没跑完」的那几档才会采用，事件流里出现没见过的状态字符串直接丢弃，不给它编一个近似档位；读旧日志遇到未知状态既不当终态也不当活着，宁可让任务留在视图里也不悄悄判死。工具条目另有自己的一套状态（`running` / `completed` / `failed` / `cancelled`，Codex 原生的 item 状态在协议层就归一到这四档），和任务状态共用了几个字面，但判定各走各的：工具条目不拿去问 `is_terminal`，这份词表守卫也不覆盖它们；计划/待办项则是 CLI 原样透传的第三套（`pending` / `in_progress` / `completed`…）。
9. 回合结局以取消位优先：worker 收尾先看 `run.cancelled`，用户按过停止就记 `cancelled`，即使这一轮随后自己跑完或报错也不改口——界面上「我停了它」比事后到达的协议结局更贴近用户事实。停止时所有待答复请求立刻广播 `invalidated`，之后进来的答复一律拒绝（「任务正在停止，请求已失效」），不会在已停的回合上补授权。
10. 同一会话同时只允许一个回合（登记按会话 id 互斥，全局并发上限 8），同项目不同会话允许并行；排队上限每会话 32 条、全局 256 条，超限如实报「任务队列已满」。

### 5. 图片附件：粘贴、选择器与拖拽

1. 三条入口共用同一段结算：输入框粘贴、`@tauri-apps/plugin-dialog` 的 `open()` 文件选择器（capability 里已有 `dialog:default`，不用新增权限）、以及 Tauri 的拖拽投放。粘贴仍要合并 `clipboardData.files` 与 `clipboardData.items` 两路（WebView2 在不同剪贴板来源下常常只填其中一路），只收 `image/*`，再按「文件名 + 字节数 + MIME + 最后修改时间」去重，避免同一次粘贴被当成两张图。
2. 上限只有一个来源：后端 `images.rs::MAX_IMAGES` / `MAX_IMAGE_BYTES`，面板进会话页时用 `ai_runtime_image_limits` 读回一次，再用于占位与提示。前端不再自己写死 8——那条重复的数字只会和后端慢慢错开。总开关关闭时命令直接拒绝，读不到就用初始兜底值，不猜后端放宽了。
3. 交出去的内容一律不被信任：粘贴把文件读成 data URL 交给 `ai_runtime_save_pasted_image`，选择器与拖拽交本机绝对路径交给 `ai_runtime_save_image_file`——后者先按 stat 卡住「普通文件、非链接、非空、不超 8 MiB」，再读真实字节。两条路都只认文件头判格式（PNG / JPEG / GIF / WebP），声明的 MIME 必须和真实内容对上，把可执行文件改名成 `.png` 会在内容嗅探这一步被拒；选择器与拖拽是把文件复制进沙箱后让 CLI 只读副本，用户选中的原文件不再被任何一方改写或被 Forge 长期持有。
4. 落盘位置是应用缓存目录下的 `ai-pasted-images`，写入用 `create_new` + 时间戳 + 进程号 + 自增序号，按来源分前缀（`paste-` / `file-`），绝不覆盖已存在的文件；缓存根和每个文件都单独检查不是符号链接或 Windows reparse point，再 `canonicalize` 一次，否则「沙箱」可能被一个链接指到任意目录。回显走 asset 协议，授权在每次加载会话页时重新建立（进程级，重启后自动恢复）。
5. 「这张图还在被历史用着」用一个同名 `.ref` 哨兵表达，而且只在用户事件**成功落盘之后**才写：写在前面会在消息其实没发出去时留下一张没人认领、又不敢删的图。加载会话页时顺带为老历史补标记（那之前的日志没有对应哨兵），否则这次的改动会把已有会话的图片当成孤儿。
6. 移除按钮真的删盘：`ai_runtime_delete_image` 只接受规范进沙箱的路径，且带 `.ref` 的一律拒绝并回一句「已发送的图片请随会话一起删除」——已经进历史的图不能从磁盘上抽走，那是回显变空白最直接的做法。清理两处：进程首次建立 asset 授权时扫一遍缓存目录，删掉没有 `.ref`、已超过 30 天、且名字是生成形状的托管文件（别人的文件不动）并回收悬空的 `.ref`；删除会话时先读那会话 `events.jsonl` 里列出的图片路径，连图和标记一起删。这条读穿不设提前收工的大小门槛：这里是带 `.ref` 标记的附件唯一的删除入口，跳过整份日志就等于把那条会话的图永久留在沙箱里（实测有一条 32.7 MB 日志的会话正踩在旧上限外）。只留一道 1 GiB 的保险丝挡失控日志——到那个量级宁可留文件，也不能冒「读截断→误删」的风险。
7. 发送路径两处复核，不是一次性信任：入队前把所有路径规范成沙箱内的绝对路径并重新读一遍内容校验；工作线程真正启动 CLI 前再校验一次，因为排队期间文件可能已被删除或被换掉。任一环节不过就整条消息失败，不会带着越界路径启动。
8. 传给 CLI 的方式按各家协议分别处理：Claude stream-json 需要内联 base64 内容块（读取发生在工作线程，不卡前端粘贴），Codex 用原生 `localImage` 输入项、只交路径由 CLI 自己读文件。两个形状都按本机 `0.163.0` app-server schema / Claude 文档核对过，各有协议层单测。
9. 斜杠命令与图片互斥，前后端同判：原生命令的文本会被直接交给 CLI，夹一条 base64 图片既没有语义也容易把参数改写。只带图片、不写字也是允许的。发送后附件路径随用户事件一起进事件日志，重新打开会话时按 asset 路径回显；回显的那张图读不到时不再摆一个空白，而是明确标成「图片已不在本机缓存中」。
10. 一次投放里的多张图逐张结算（`Promise.allSettled`）：`Promise.all` 会在第一个失败时把整批结果一起丢，那张失败的图连带其余**已经落盘**的附件都不进输入框——既看不见也没人删，只能等着堆在缓存目录里。现在成的照常用，败的报第一句原因；`pendingImages` 仍按整批占名额，避免连续投放越过上限。这段结算在 node 环境的组件测试里观测不到（附件是组件内部 state，`renderToStaticMarkup` 每次重挂），只做了类型检查与人工核对。
11. 拖拽只有一个整窗监听：Tauri 在 `dragDropEnabled` 默认开着时不给 DOM `drop` 任何文件，只能走 `getCurrentWebview().onDragDropEvent`，而它给的坐标是相对 webview 的**物理像素**，除以 `devicePixelRatio` 才能和 CSS 布局比。整窗监听（打开文件到工作区）保持唯一，输入框用 `src/lib/dropOwner.ts` 把自己注册成一个可认领投放的局部目标，命中就整条接管本次 enter/over/drop——落在底部输入框的图片不再同时被工作区当成「打开这个文件」。后注册的目标在上层，所以嵌在侧栏里的输入框优先于整窗路由；`leave` 只熄灭高亮、不认领，没有命中任何局部目标时原样交给整窗逻辑。

### 6. 会话界面：折叠、跟随、草稿与回合动作

1. 正文渲染走文档预览同一套 `lib/markdown.ts`：高亮与文档预览、编辑器共用同一份 Lezer 语法表与 `--syn-*` 色板，安全白名单仍是聊天自己的严格版本。复制按钮是注入 HTML 字符串的一部分，所以由根节点上的一次事件委托响应，而不是逐块挂 React `onClick`。原来那颗「复制整条回复」的按钮已移除：整条复制会把多个代码块和散文混成一坨，按块复制才是用户真正要的东西。指向本地文件的链接（`src/a.ts:12`、`./a.md#L9`、`C:\repo\a.ts`、`file:///…`）由 `lib/fileLinks.ts` 认出来，渲染成带 `data-file-path` / `data-file-line` 的锚点，点开走 `docs.openHit` 那一跳，和终端链接、搜索命中同一条路：相对路径按工程根还原，网页地址与协议相对的 `//host` 先排掉，`~` 定位不了就不当文件。工具卡片上的路径同一套开关：摘要只有一个目标时整行可点，明细里每条动作行、每个补丁头各点各的，底部「本轮改过 N 个文件」的列表也能点；行号只取官方字段（Read 的 `startLine`、补丁头的 `+N`），没有就跳到文件本身而不编一个。回调由 `AiFileLink.tsx` 的上下文递下来，没有回调的场合退回普通文字，不会画出点不动的按钮。
2. 时间线先折叠、再开窗。连续 ≥3 条工具调用或推理摘要折成一段，审批卡、正文、用户消息和文件改动永远单独渲染；正在跑的那一段默认摊开——把还在动的工具藏起来，等于把「它还在动」这个事实藏起来。一屏最多 120 项。往上翻只有一个入口：窗口里还藏着的先放出来，放完了且后端说还有更早记录时，才用 `ai_runtime_load(before_seq)` 要更早的一页，并顺手把窗口一起放大——只取回更老的内容而不放开窗口，那一页照样看不见。顺序不能反：先开窗会把一整段过程劈成两半，两段都不够折叠门槛，就都摊在屏幕上。
3. 滚动跟随用锚点而不是布尔值：离开底部时锚定当时的末尾条目 id，回到窗口下沿就清零恢复跟随；「N 条新消息」按 id 在条目列表里找位置算差值，锚点那条被历史重建换掉时报 0 而不是编一个数。用 id 不用条数，是因为翻历史会整段重建 entries，用数字锚会把重建误读成新消息。往前翻页期间保持视线不动用的是另一把锚：记下最上面那条消息离视口顶的距离，提交后量它挪了多少再补 `scrollTop`——更早的内容插在上方要补，正文在下方追加不该补，按整个 `scrollHeight` 的差值补会把人推离正在读的那一段。
4. 「回到底部」是浮标，绝对定位必须钉在滚动视口上：放进滚动容器内部会跟着内容一起跑，滚上去就看不见，所以外面套一层只负责定位的 `.ai-chat-viewport`。
5. 草稿按会话进 localStorage，发送历史按工程共享（草稿上限 2 万字符，历史 50 条、单条 2000 字）。斜杠命令不进历史：它当场就执行完了，召回一条 `/compact` 只是让人再发一次已经跑过的指令。↑↓ 只在命令菜单没出现、且光标停在首/末行时才接管，否则归光标；Esc 退出召回时把用户在召回件上改出来的那行还回去，替换整段文本后光标落到末尾。
6. 审批卡出现哪些按钮由 `permissionOffer` 依据请求本身判断，不按工具名猜：认不出工具名就没有「不再询问」，拿不到绝对目录就没有「按目录」，后端没声明 `canEdit` 就没有「改完再允许」。宁可少给一个按钮，因为前端把按钮画全而后端兑不了更糟。
7. 回合的错误挂在**这一回合**上：`AiTurnActions` 在时间线结尾显示最近一回合的失败原因加「重试 / 重新生成」，输入框上方那条 `.ai-session-alert` 只兜住没有回合归属的那一句，同一句话不出现两遍。重试永远由用户点出来，运行时绝不自动重发；只有最近一回合能重来——更早的回合重发会带上它之后的一切上下文，那不是重试。斜杠命令的原文不重发：命令目录、参数改写与本地命令都在发送那一步才决定。
8. 压缩的判定按用户阈值（默认 80%）算，自动那档不早于 90%、且只在本轮报告过的分母上动手，记忆到的窗口只够提示。自动触发还会让位于：输入框的半截话、未发送的排队项、待答复的授权、正在停止。面板代打的 `/compact` 走与手输完全相同的校验与信任闸门，并且不动用户输入框里的内容和已经贴好的附件；上一回合本身就是压缩时不再连发，否则摘要没能把比例降到阈值以下就会一轮接一轮折下去。
9. 流式事件用 rAF 合并，但只推迟「什么时候通知订阅者」，快照照旧当场写进 store；词表之外的任何事件类型都算紧急，宁可多通知一次也不让状态变化多等一帧。会话面板靠这份合并把重渲染压到每帧一次。
10. 压缩的入口和操作都在 token 芯片点开的那一层（`AiCompactPanel`）：想知道占用就会点占用，动作理应长在同一个地方，所以输入框上方不再另起一条横幅。到阈值时芯片上一个点，正在压缩时芯片写「压缩中」、标题状态说「正在压缩上下文」、进度条那一行给出它在干什么——CLI 折上下文那几十秒只转进度条，等于让人以为卡住了。
11. 对话列只放对话。待答复的审批卡、没有归属的错误、正在跑的这一轮和排队项都钉在输入框上方的 dock 里（`.ai-session-requests` / `.ai-session-alert` / `.ai-session-progress`），本轮改过哪些文件收进底栏（`.ai-edit-summary` 点开往上浮）。理由很实在：审批卡跟着历史一起滚出屏幕，等于本轮卡住了却看不见卡在哪；几百条消息里再摊一条状态条，找它比找消息还难。排队条默认摊开——排队的意义就是还能改主意。
12. 消息导航列的是**整个会话**的轮次，不跟着正文分页走。正文一页只装得下 500 条事件，长会话里一轮工具输出就能把它填满，导航照着 `runtime.entries` 画就只剩一条记录。所以另有 `ai_runtime_outline`：从事件日志**尾部倒着**扫，只留每条 `user` 事件的序号、条目 id、首行摘要和该轮 `files` 事件的去重路径数，一次列全（够 2000 轮就停，并如实报「没数到会话开头」）。它和 `search` 一样不拿 `IO_LOCK`——扫长日志期间卡住事件写入不值当；也只在第一次展开面板时才扫，没点开就没必要读盘。列表按 200 行一档，往上滚一档加一档，加出来的行插在上方，靠 `scrollHeight` 的差值补 `scrollTop` 让视线不动。芯片上的数字：索引没取回时只报正文里那些并带个 `+`，宁可报约数也不报一个确定的小数。
13. 导航的摘要与文件数在两边同一个口径：正文里已加载的那几轮以正文为准（索引只是面板打开那一刻的快照，正在跑的那轮还在长），文件数按路径去重、只数 `files` 事件里真正落盘的改动，跟底栏那份汇总一致。点还没加载进正文的那一行，先按序号把中间的事件**连续**补回来——走的是「更早」那条路径，游标一路往前挪，中间不留没读到的空洞，否则时间线就成首尾相接的两半；够到目标才滚，补到愿意付的上限仍够不着就如实说一句，而不是让点击没有反应。跳转前放开窗口用的是「目标到末尾的条目数」：时间线项不会多于条目，一次算准，不用「找不到就加大一档」地试八次。
14. 卡片收尾分得清「已处理」和「已失效」，不再用一句「已处理或失效」把两件事混成一件：答复成功时那条 `invalidated` 事件带上答案本身，投影挂在 `request.answer` 上，于是重开会话后卡片仍能把当时选的那几项还原出来（命中选项的算选中，没命中的就是「其他」里手打的那句），另一个窗口答的也走同一条路；没有答案却失效了（停止、进程结束、同工具的请求被后来的顶掉）就明说是没等到答复，不给人留一个「好像我答过」的错觉。提问卡的选项整行都是点击区，带 hover 与选中底色，`description` 从悬浮提示提到第二行——原来只有那颗小圆圈能点，行间还留着 7px 死区，点不中又容易误触。
15. 提问卡（`AiQuestionCard`）照 codeg 的 `ask-question-card` 重画，不再是一张平铺的表单：多题时进度条顶到卡片边缘、页签一次一题（挂 `header` 那种短标题，不是整句问题）、正文按最高那道题定高（页签之间来回切不会把卡片抽得忽高忽低）、单选点完自动跳下一题。选项一律做成整行卡片，`description` 排第二行，`(recommended)` 从正文里拆出来做成徽标——提交与回显仍按原文那份 label 走，改的只是显示。「其他」排在所有真选项之后，点中才就地长出一个输入框，写了字就算答完这题；单选再点已选中的那项等于取消。没有「跳过」：后端要求每题都给一个非空答案（Claude 侧 `answers` 的数量必须和问题数相等），给一颗兑不了现的按钮比少画一个更糟。答完的卡在时间线里收成一行「提问回答：…」，点开才是整张只读卡，版式和刚才答的那张一模一样——只读那份的选择直接从答案算，不另养一份本地状态，也就没有两边各说各话。答复在途时整卡变暗、页签仍可翻，控件全在 `<fieldset disabled>` 里，不用逐个点禁用。

16. 没有正文的思考块不摆成一行「思考」。两家 CLI 都会送来点不出东西的思考：Codex 的加密推理只给占位摘要，Claude 的 redacted thinking 只剩签名——实测两份 Claude 会话的 44 条思考事件里 32 条正文为空，时间线于是排出一长串「思考」，每一条展开都是空白，看着像界面坏了。判定放在 `groupAiTimeline` 而不是投影里：事件照原样落盘（那是模型确实想过、只是不给看的证据，重放历史也还有它），只是不进渲染；`liveThinking` 认下唯一的例外——本轮还在跑、而且它正是末尾那条，此时空正文就是「正在想」的凭证，不返回摘要的模型自始至终只有这一条空的。同一份判定也管住标题：「正在思考」只给那一条，不再因为本轮在跑就给每条思考都写「正在思考」（对照 codeg：流式路径留，历史路径丢）。思考条数因此和折叠段的「N 次思考」同一个口径——数出来的就是看得见的。

17. 消息导航的跳转是一份状态，不是一次 `querySelector`。目标可能要等历史补齐、也要等时间线窗口放开才存在于 DOM 里，而这两步各自都会重新渲染：旧写法在点击的闭包里轮询 6 次 ×60ms，`await` 补完历史以后手上的 `entries` 还是跳转前那一份，找不到条目就静默不跳——症状正是「点了没反应，往上滑一下再点才到位」（滑一下触发重渲染，第二次点击才带着新的 entries）。现在 `jumpToTurn` 只记下目标（`waiting` 说明还在为它补历史，补完之前不算够不着），真正滚动的是依赖 `pendingJump + entries + timeline` 的 layout effect：条目不在正文里就直说「这一轮太早，还没加载到」；在正文里但被窗口挡着就按「目标到末尾的条目数」一次放开，下一帧再滚；落地用 `block: "center"` 直接到位并闪一下，不用 smooth——补历史期间视图本来就在动，平滑滚动会被下一次提交接着拽走。跳转一开始就落锚点：否则每补一页事件，那条「贴底就跟随」的 effect 都把视图拽回最后一条。行序号判的是 `seq !== undefined`，写成真假判断的话序号 0 的那一轮永远跳不到。导航面板按会话 `key` 挂载，切到别的对话不该带着上一份的选中行与已展开档数。行本身也按序号归位：索引一次最多列 2000 轮，正文里比这更早的轮次以前是接在列表末尾的，于是最老的一轮排到了最下面，还被「先露最近 200 行」当成最新那一档露出来——投影因此要给 `user` 条目带上事件序号（本机刚按下、还没落进日志的那几轮没有序号，它们确实最新，排最后正合适）。
18. 已结束的历史不是待办任务。投影里每条 `user` 事件曾顺手造一轮（没有状态事件就写 `submitting`），而导入的原生历史整份日志共用一个 runId、一条状态事件都没有，于是几百轮已经结束的消息被摆成输入框上方一行「正在提交/排队中」：按立即执行、编辑、取消，后端只回「这条任务不在当前窗口的队列里」——它本来就不存在，是界面凭空造的。现在 `user` 事件只写进时间线，顺带记住这一轮的正文（`running` 状态事件自己没有 prompt，就从这份记录里取）；一轮只有在**真有状态事件**或**本机 IPC 往返中的占位**存在时才进任务列表，而占位在它自己那轮的事件落地后就让位。队列 strip、`latestTask` 错误行、停止按钮由此都只认真实存在的回合。
19. 队列属于哪一个窗口，就说清是哪一个：排队队列活在**收下它的那个进程**的内存里（每会话 32 条、全局 256 条），不跨窗口共享。事件日志是共享的，所以另一个窗口排的任务本窗口也看得见，但按立即执行/编辑只能失败。旧文案一句「排队任务不存在」把两种真原因（已经开始或结束、由另一个窗口排队）压成一句像界面坏了的话；现在后端的八处队列查找共用 `NOT_QUEUED_HERE`，明说「不在当前窗口的队列里……排队时用的是哪个窗口，就到哪个窗口操作」，前端那三处本机守卫另说「已经不在本窗口的待办列表里」——判定的层次不同，话也分开说，不拿后端那句盖本机这份快照。跨窗口真正接管队列需要另建持久队列，会引出「谁有权停止谁的回合」一堆新问题，当前没有这个需求，不做。
20. 同一次压缩只排一遍，配对在**后端读事件那一层**做（`store.rs::compaction_fold`）。一次压缩经两条通道到达：实时事件只报边界（Claude 连 token 数都只给状态，摘要正文一个字节都没有），正文只存在于原生历史里，而捞回来是**追加到 Forge 自己日志末尾**的——于是它拿到最大的序号、渲染到时间线最下面，同一次压缩出现两遍，第二遍还离原位几千条远（实测 c3314013：实时压缩在 seq 1183/2379/4013/5262，捞回来的摘要在 5366/5367，全日志 5370 条）。前端修不了：它只看得到当前这一页（一页 500 条事件），两张卡很少同页，按页折叠注定时对时错；日志只追加、序号不能断，也不能把摘要那条挪走或删掉。所以配对扫的是整份日志：认得出来就把正文并进那一段**最后一条**事件的 `text`（并到末尾而不是开头，首屏只装得下日志尾部时也带得上），摘要那条本身不再进页，页预算按并宽之后的行宽算；认不出来就原样留着，宁可多一张卡，也不把摘要贴到另一次压缩上。认亲优先用后端盖在实时事件与摘要上的 `episodeId`，旧日志没有这个标识就按顺序认，但还要过字节偏移那一关（实时事件记着当时原生历史的起点 `sourceStart`，摘要的 `summaryId` 里带着自己的偏移，偏移落在起点之前的绝不许靠顺序硬凑）。正文搜索按同一份口径改报命中位置（`search.rs`），否则点进去跳的是一条界面上根本不存在的卡片。摘要那条的 `status` 是投影时写死的 `completed`，它并不知道那次压缩是怎么结束的，所以永远不许改写卡片上已经观察到的状态——取消掉的那次仍显示「已中断」。
21. 回合末尾的文件汇总卡按**一轮对话**切分，不按 `runId`。整段从原生日志导入的会话每一条都写着 `runId="native"`，按 runId 切会把几十轮的改动压成时间线最末尾的一张卡，底栏那个数字还会随着往上翻越长越大（它本该只报「这一趟」）。现在按「一条用户消息到下一条用户消息之间」分组，每组把卡挂在自己最后一条顶层条目之后，底栏只取最新那一组；正在跑的那一组先不挂卡，改动还在往里加，挂上去就是一张数字一直跳的卡。子代理的改动归它自己的委派卡，不进主时间线这一轮。
22. 翻页不再从头读整份日志：会话目录里多了一份 `events.idx`，每 64 条事件记一次「序号 → 字节偏移」，另外存下最新序号、未终结任务、最后一条状态与压缩配对素材。翻页时 seek 到最近的锚点、只解析这一页附近，往前翻第 20 页和第 2 页一样快；打开会话也不再为了拿最新序号把整份日志重新解析一遍。这些原本都是「要看完整个文件才算得出来」的东西，所以以前那句「整份扫描不能省」现在改成「整份扫描只在索引缺失或对不上时发生」。**索引只是缓存**：内容全部由日志推导，比日志短就只补读新增的那一段（追加是唯一的写形态），比日志长（日志被截断）或中段损坏就整份重建；索引坏了、版本不符、锚点与行边界对不上，这一页照旧全量扫描并把索引删掉重来——宁可慢一页，不能给错页。往前翻要求凑满一页：被挡掉的系统注入和被并走的摘要不占条目，只数事件会挑到一段只剩注入的区间，于是短了就往更早一个锚点退，退到日志开头为止（那才是真的没有更早了）。实测 10.4 MB / 35159 行的会话：一页从 326 ms 降到 3 ms，打开会话从 149 ms 降到 1 ms；首次没有索引时仍是 150 ms 上下的全量构建，之后一直走索引。

## 斜杠命令与参数

输入 `/` 可发现和补全命令；进入参数区后保留用法提示，Ctrl/Cmd+Enter 执行。Forge 本地支持模型、强度、权限、Fast、上下文和设置入口；Claude 从真实会话目录发现可适配命令并在每次派发前复核；Codex `/compact` 与 `/review [instructions]` 使用各自专用 RPC。未知命令不作为普通模型消息发送，原生参数中的引号和换行不做 shell 解释。

两家 compact 参数不同：Claude 支持说明参数；Codex 0.163.0 的 compact RPC 只有 threadId，附加参数明确拒绝。完整支持范围、权限确认、费用风险及协议证据见 [斜杠命令协议](slash-command-protocol.md)。

## 安全边界保持不变

默认关闭、项目可信确认、未保存文档拦截、同会话 FIFO、未知审批拒绝、停止与进程树清理、落盘后广播、失败不自动重发均保留。同项目不同会话允许并行。不按 CLI 版本号拦截启动：装哪个版本都能聊，能力差异靠运行时探测。

## 当前限制与验收要求

- 原生 JSONL 属于供应商本地格式，不是长期稳定的跨版本协议。首次发现会跳过无法核验的损坏、超限或其他项目文件；已发现会话后续同步失败时保留已有镜像并显示读取警告。续聊校验失败时拒绝启动。未知记录类型不会伪装成已支持的功能。
- 会话标题自动取，用户不用自己改名：新建会话不留占位名（不给 Claude 传 `--name`，也不给 Codex 写线程名——那两个都会在原生历史里落一条最高优先级的名字，把自动标题永久压住），首条用户消息发出后按 `auto_title` 命名：取第一行、折叠空白，超过 30 字先断在第一句，其次断在空格。原生历史走同一个函数，两个来源写的必须是同一个字符串。CLI 自己有的标题优先：Claude 按 `customTitle` > `aiTitle` > 首条真人消息（改名记录落在长会话末尾也能补读到），Codex 读 `session_index.jsonl` 的 `thread_name`（早期版本把整条首句写成线程名的，仍按 `auto_title` 收窄）。旧数据里「Claude Code 会话 N」这类占位名一律忽略并就地纠正。实测本机 Claude 2.1.308 与 Codex 0.164.0 在 `-p` / app-server 下都不生成 AI 标题（`~/.claude/projects` 全量 `ai-title` 为 0 条、rollout 无 `thread_name_updated`），所以名字出自首条消息而不是模型摘要；`ai-title` 哪天出现了会自动顶上去。用户在 Forge 改名后置 `title_locked`，之后的自动同步不再覆盖。
- 不提供跨项目的全局历史页面、其他项目入口、分支树、文件回滚、后台子代理管理或完整终端 slash-command 覆盖（已适配的命令见上节）。正文搜索只覆盖当前项目，且不做语义/模糊匹配。本轮不是两家官方终端界面的逐项克隆。
- 粘贴图片按内容头认格式、按沙箱根认路径，但「CLI 真的看得懂这个绝对路径」还没在真实账号上验证过：Codex 是自己按 `localImage` 的绝对路径读文件，供应商是否允许项目外的路径、Claude 的 8 MiB 内联 base64 会不会撞上 CLI 自身的输入上限，都只有协议层的形状保证。拖拽依赖 Tauri 的整窗回调，`devicePixelRatio` 变化（缩放、多屏）时的命中只做了换算与单测，没在真实多屏桌面上量过。
- 附件的清理是尽力而为：`.ref` 写失败（磁盘满、权限）时那张图会被当孤儿，30 天后可能被回收——好在每次加载会话页都会补标记，重新打开一次就把它认领回来。孤儿回收只认 `paste-` / `file-` 的生成名形状，往缓存目录里放别的东西不会被删；删除会话时整份日志读穿再回收，不再有「大会话的附件留下」这一档，只有单份日志超过 1 GiB 这种失控情况才跳过（那时宁可留文件）。
- 输入框认领的是整次投放，不看类型：把一堆源码文件拖到底部输入框上，它们会被附件入口接管并逐条报「不是支持的图片」，而不会退回工作区去打开。认领发生在路由那一刻（`dropOwner` 没有反悔通道），要按类型放行就得让整窗监听懂附件规则——那等于把沙箱判定抄第二遍。目前的做法是：只在输入框区域高亮「松开以附加图片」，看见高亮还扔源码文件就按错误提示处理。
- Forge 只互斥自己的同会话任务，不禁止其他 CLI 窗口存在。外部状态是快照，Claude 没有与 Forge 共享的原子任务锁；Codex 的线程写锁则真的挡复用，所以发送前直接试那把锁：握着就排成「等待外部任务」，等下一轮轮询重新判定，而不是起进程再吃一句英文错误。万一还是撞上（同瞬间另一个窗口抢先），Codex 回 `already has an active writer` 时界面说清是「另一个窗口或 CLI 占着这条会话」并给出办法。Windows 已实现 Claude PID 创建时间核验，Unix 尚未完整支持；Codex 尾部缺少任务边界时显示未知。
- 对正常追加的主会话日志做顺序投影；尚未实现 Claude 分叉/rewind 的完整 parentUuid 活动分支重建。
- 删除会话是「锁内等到底」的唯一例外：那一条 CLI 若卡住，其他会话的发送与队列调度最长会被按住 15 秒，随后仍只报「任务仍在清理」，不会更强地杀进程或假装已停。普通停止与关闭项目不受此影响。
- 状态词表两边只能靠字面量对齐，改名等于改已落盘的数据格式；测试只保证「后端会发出的那几档」一致，不能证明 CLI 永远不会返回没见过的措辞——未知措辞一律按未知处理，不猜成终态。
- 时间线的折叠与开窗都是显示层：120 项是「一次铺多少条」，不是虚拟滚动，DOM 不会随滚动回收；折出去的过程条目仍完整留在事件日志里，展开后逐条照原样显示。语言高亮由聊天 worker 里的 Lezer 语法表负责（与编辑器同一张表），认不出的围栏当纯文本块处理，不报错也不猜语言。
- 草稿与发送历史存在 WebView 的 localStorage：上限是本地防丢的（草稿 2 万字符、历史 50 条），换设备、清缓存或换 Webview 数据目录都会丢，不跨设备同步。「重试 / 重新生成」都只是把同一句提示词再发一遍，供应商端不保证幂等——上一轮已经写进文件的改动，重来等于再来一次同样的动作。所以两个按钮一律由用户点出来，运行时绝不自动触发，也没有「撤销这一轮」的配套能力。
- 原生镜像没有磁盘索引：Forge 自己的 `events.jsonl` 现在有了（`events.idx`，见会话界面第 22 条），但发现原生会话、正文搜索和轮次索引仍是线性扫描，只是把扫描量限制在上面的预算内，超限就标记不完整，而不是悄悄少给结果。搜索读磁盘，不共享前端内存里的实时快照：运行中的回合按批落盘（64 KiB / 128 个事件，并有 32ms 周期 flush），搜索框看到的尾巴可能比聊天区慢一批。命中数按合并后的片段计，一条被拆成 N 次流式输出的消息可能占满单会话 5 条的额度。大量历史需要进一步性能验收。
- 自动测试只使用合成历史、模拟 IPC 与本地模拟 CLI。本轮没有读取开发机真实聊天正文、调用真实模型、花费账号额度或重启用户程序。
- 真实账号续聊、真实 CLI 返回的模型目录/用量、Windows 桌面布局和交互仍待人工验收；需要用户重启 Tauri 加载新增 Rust 命令。
